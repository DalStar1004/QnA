## 001 · 2026-08-27 · 목표 글자 수 기능 제거 + 게임 배경 선명도 개선

**요청한 내용**

> word_connection_game_v2.html코드에 목표 글자 수 기능을 제거하고 글자수에 관계없이 답을 맞출수 있도록 개선하고 게임배경은 기본색이 있어서 뚜렷하게 나오지 않는다 게임배경색이 잘 나오도록 개선한다

**AI가 한 일**

1. **목표 글자 수 기능 제거**
   - 설정 모달에서 `🔤 목표 글자 수` 입력칸 삭제.
   - `Dictionary`를 글자 수 기준 조회에서 블록 개수 기준 조회로 교체
     (`getWordsByLength` → `getWords` / `canFit` / `pickWordPair` / `hasWord`).
   - 정답 판정에서 `"글자 수 불일치!"` 분기를 제거. 목표 단어이거나 같은 카테고리 사전에 있는 단어면
     길이에 관계없이 정답으로 처리.
   - 블록을 하나만 눌렀다 뗀 실수 클릭은 콤보 손해 없이 선택만 해제.
2. **게임 배경 선명도 개선**
   - 원인: `body.has-bg`에 크림색 스크림이 **불투명도 0.62** 로 덮여 배경 그림이 뿌옇게 보였음.
   - 스크림을 0.10~0.14 수준으로 낮추고, 배경 이미지 로딩 중 흰 화면을 막기 위해 `background-color` 추가.
   - 화면을 크게 가리던 보드 카드를 반투명 유리(`backdrop-filter: blur`)로 바꿔 배경이 비쳐 보이게 함.
   - 배경 위에서 글자가 묻히지 않도록 제목/블록/버튼 그림자를 `body.has-bg` 전용으로 강화.

**검증** — 브라우저 렌더링 확인, 남은 `currentLengthLimit` 참조 0건.

## 002 · 2026-08-27 · 글자 수 안내 위치 이동 + 카테고리 파일 추가 기능

**요청한 내용**

> word_connection_game_v2.html코드에 글자 수 제한없음 글을 게임을 진행하는 화면에 잘보이는 곳으로 옮기고 카테고리는 파일로 추가해서 생성할 수 있도록 기능을 수정해줘

**AI가 한 일**

1. **규칙 배너 신설** — 설정 모달 안에 있던 안내를 빼고, 점수판과 단어 보드 사이에
   `[🔤 글자 수 제한 없음] 2글자든 5글자든, [카테고리]의 단어면 모두 정답!` 배너를 상시 노출.
   현재 제시어가 배너 문구에 자동 반영됨.
2. **카테고리 파일 추가 기능** — 설정 모달에 `📂 카테고리 파일 추가` 섹션 추가
   (파일 선택 / 예시 파일 받기 / 추가된 카테고리 목록 + 개별 삭제).
   - 지원 형식: JSON(`{"이름": ["단어", ...]}`, `[{category, words}]`), TXT/CSV(한 줄에 카테고리 1개).
   - `CategoryManager` 신설: 파일 파싱 → 한글 2~10글자 단어만 통과 → 중복 제거 →
     `localStorage` 저장 → 기본 사전과 병합.
   - 기본 사전은 `BUILTIN_DICTIONARY`에 원본 보관하여, 추가한 카테고리를 지우면 원상 복구.
   - 제외된 단어·형식 오류는 토스트로 안내.

**검증** — 헤드리스 Chrome 자동 테스트 25개 항목 통과
(JSON/TXT 파싱, 잘못된 단어 제외, 프로토타입 이름 거부, 목록 반영, 삭제 후 복원 등).

## 003 · 2026-08-27 · 작성 예시 버튼 + 음소거 버튼 이동 + 클리어 종료

**요청한 내용**

> (파일 형식 설명 부분을) 작성예시 버튼을 예시 파일 받기버튼 옆에 만들어서 클릭시 내용을 볼수 있도록 하며
> 음소거 버튼을 단어변경 버튼이 있는 줄의 맨 왼쪽으로 이동시키며 정답을 모두 맞출시 게임을 끝내도록 한다

**AI가 한 일**

1. **작성 예시 버튼** — 길게 노출되던 파일 형식 설명을 `작성 예시 ▾` 버튼 안으로 접음.
   펼치면 JSON/TXT 실제 파일 모양의 코드 블록과 규칙이 보이고, 설정을 다시 열면 접힌 상태로 시작.

## 007 · 2026-08-28 · 스무고개 라운드제 도입 + 힌트 6개 제한

**요청한 내용**

> word_connection_game_v2.html코드에 스무고개를 시작할때 몇번을 스무고개를 진행할지 물어보고 카테고리를 입력해서 문제를 내고 한번 끝나면 다시 카테고리를 입력해서 스무고개를 진행하는 방식으로 게임을 만든다

> 작업기록에 입력한 prompt와 작업한 내용도 같이 추가해준다

**AI가 한 일**

1. **스무고개를 '세션 + 라운드' 구조로 재구성** (신규 `QuizSession`)
   - 006에서는 `스무고개 시작` → 카테고리 입력 → 한 판으로 끝났는데,
     이제 **횟수를 먼저 묻고 → 라운드마다 카테고리를 다시 입력**하는 흐름으로 바꿨다.
   - `QuizSession`이 총 라운드 수·현재 라운드·누적 점수·라운드별 기록(`history`)을 들고 있고,
     `QuizManager`는 '지금 한 라운드'의 힌트/정답만 맡는다. 둘의 역할을 나눠 라운드가 넘어가도 상태가 꼬이지 않게 했다.
   - 화면 흐름: `openQuizSetup`(횟수) → `startQuizSession` → `openQuizRound`(카테고리)
     → `startQuizRound`(문제 생성) → `beginQuizPlay`(판) → `showQuizRoundResult`(라운드 결과)
     → `nextQuizRound` → … → `finishQuizSession`(최종 결과).

2. **모달 3개 신설** — 기존 모드 1 결과 모달과 섞이지 않도록 모드 2 전용으로 분리했다.
   - `quizSetupOverlay` — 카테고리 입력칸을 빼고 **`🔁 스무고개 횟수`(1~10회, 기본 3회)** 를 받는다.

   - `quizCategoryOverlay` — 라운드마다 열리는 카테고리 입력창. 제목에 `N라운드`, 안내에 `M번 중 N번째`를 표시하고
     입력칸은 매번 비운다. Enter 키로도 바로 문제를 받을 수 있다.
   - `quizRoundOverlay` — 라운드 결과. 정답 공개 + 이번 라운드 점수(`+N`) + `N / M 라운드 · 누적 K점`.
     버튼은 마지막 라운드면 `최종 결과 보기`로 바뀌고, 이때는 중복되는 `그만하기`를 감춘다.
   - `quizFinalOverlay` — 최종 결과. 총점, `M번 중 K번 맞혔어요`, 라운드별 목록(라운드·정답·카테고리·본 힌트 수·점수),
     전부 맞히면 우승 트로피, 신기록이면 뱃지.

3. **힌트를 6개로 한정** (`QUIZ_HINT_TOTAL` 10 → 6)
   - 구성은 **LLM 힌트 3개 + 확정 힌트 3개**(글자 수 / 초성 / 첫 글자)다.
     006의 확정 힌트 4개에서 `마지막 글자`를 빼 3개로 줄였고, 확정 힌트는 여전히 절대 잘리지 않는다.
   - LLM에는 다듬는 과정에서 버려지는 문장을 감안해 4개를 요청하고(`QUIZ_LLM_HINT_REQUEST`) 3개만 쓴다.
   - 내장 사전 대체 문제(`offlineQuiz`)의 앞부분 힌트도 3개로 맞췄다.
   - 힌트가 줄어든 만큼 한 라운드 제한 시간은 `6 × 10초 + 여유 20초 = 80초`, 만점은 6점이 된다.

4. **점수·기록 처리**
   - 점수 카드는 **세션 누적 점수**를 보여준다. 라운드를 시작할 때 `GameState.score`를 누적값으로 되돌려 놓고,
     라운드 몫은 `이번 판 점수 − 직전 누적`으로 떼어 낸다.
   - 모드 2 최고 기록은 라운드마다가 아니라 **세션이 끝날 때 총점으로 한 번만** 갱신한다.
   - 라운드 칩(`🤖 N / M 라운드`)과 힌트 패널 제목(`🤖 스무고개 N/M`)에 진행 상황을 표시한다.

5. **중간 이탈 처리**
   - 카테고리 입력 단계에서 `그만하기` — 이미 푼 라운드가 있으면 최종 결과를, 없으면 그냥 세션을 접는다.
   - `게임 종료` 버튼이나 모드 전환은 남은 라운드까지 정리하고 열려 있는 모드 2 모달을 모두 닫는다.
   - 문제 생성 중에 세션이 취소되면 응답이 늦게 와도 판을 열지 않는다.

6. **정리** — 모드 1 결과 모달에 임시로 넣어 뒀던 모드 2 분기(`info.quiz`, `#gameOverAnswer`)를 제거해

012 에서 찾은 문제(콜드 상태 첫 요청이 115초 → `REQUEST_TIMEOUT` 60초를 넘어 끊김)를 고쳤다.
수정 전 원본은 백업해 두고 작업했다.

1. **`LlamaClient` 에 `warmUp()` 추가**
   - Ollama 는 `/api/generate` 에 `prompt` 를 비워 보내면 **생성 없이 모델 로드만** 한다.
     이 점을 이용해 예열 전용 요청을 만들었다. (실제로 응답 본문 길이가 0인 것을 확인함)
   - 예열은 `REQUEST_TIMEOUT`(60초)과 별도로 `WARMUP_TIMEOUT`(300초)을 쓴다.
     콜드 로드 자체가 60초에 가까워서 같은 값을 쓰면 예열이 먼저 끊긴다.
   - `warmedModel` 로 **모델당 한 번만** 예열한다. 실패하면 되돌려 다시 시도할 수 있게 했다.
   - 모델 이름이 바뀌면 새로 예열한다.

2. **`KEEP_ALIVE = '30m'` 도입**
   - Ollama 기본값이 5분이라, 예열해 두어도 5분 쉬면 다시 내려가 같은 문제가 반복된다.
   - 예열 요청과 실제 문제 생성 요청(`requestOnce`) **양쪽에** `keep_alive` 를 실어
     라운드 사이에 모델이 내려가지 않게 했다.

3. **`testLlmConnection()` 에서 연결 확인 직후 예열**
   - 모델이 있는 것을 확인한 경우에만 예열한다.
   - 기다리는 동안 무엇을 기다리는지 알리도록 문구를 나눴다.
     `준비 중… (처음 한 번은 1~2분 걸릴 수 있어요)` → `사용 준비 완료`
   - 예열에 실패해도 연결 자체는 된 것이므로 경고만 띄우고 게임은 그대로 시작할 수 있게 했다.

**검증**

브라우저 확장(Claude in Chrome)을 쓰지 않고 헤드리스 Chrome 과 HTTP 직접 호출로 확인했다.

1. **예열 메커니즘 (HTTP 직접 호출)** — 모델을 내린 뒤 게임과 똑같은 요청을 보냈다.
   - `prompt:''` 예열 요청: **52.9초**, 응답 본문 길이 **0** (생성 없이 로드만 한 것이 맞다)
   - `/api/ps` 로 `qwen2.5:7b` 가 실제로 올라갔고 만료가 **30분 뒤**로 잡힌 것을 확인
   - 예열 후 문제 생성: **0.7초** (수정 전 콜드 상태 115초 → 타임아웃)

2. **JS 구문/노출 확인** — 페이지 사본에 오류 수집 스크립트를 넣고 헤드리스 Chrome 으로 열었다.
   결과: `JS_OK [LlamaClient=object, warmUp=function, ping=function, testLlmConnection=function]`
   (오류 0건)

3. **연결 확인 버튼 전체 흐름** — 모델을 내려 콜드 상태로 만든 뒤,
   페이지 사본에서 실제로 `testLlmConnection()` 을 돌리고 상태 문구 변화를 관찰했다.

   > 연결 확인 중… >> ✅ 연결 성공 — qwen2.5:7b 준비 중… (처음 한 번은 1~2분 걸릴 수 있어요)
   > >> ✅ 연결 성공 — qwen2.5:7b 사용 준비 완료

   실행 후 `/api/ps` 에 `qwen2.5:7b` 가 올라와 있는 것까지 확인했다.
   검증용 사본(`_syntaxcheck.html`, `_warmupcheck.html`)은 확인 후 삭제했다.

**남은 것** — 힌트에 한국어 아닌 글자가 섞이는 문제는 이번 작업 범위가 아니라 그대로 남아 있다.

## 014 · 2026-08-29 · 힌트에 한국어 아닌 글자 섞이는 문제 해결 (걸러내기 + 프롬프트)

**요청한 내용**

> 남은 문제: 힌트에 한국어 아닌 글자가 섞이는 건(.big cat., 비ONGODB) 이번 범위가 아니라 그대로입니다. 이어서 손봐줘

**AI가 한 일**

프롬프트로 부탁만 해서는 작은 로컬 모델이 규칙을 지키지 않는다.
그래서 **프롬프트로 요청하고, 코드로 걸러내고, 걸러지면 다시 받는** 세 겹으로 막았다.

1. **걸러내기 — `QuizContent` 에 화이트리스트 도입**
   - `HINT_ALLOWED_RE` 로 한글(음절·자모), 숫자, 공백, 흔한 문장부호만 허용한다.
     영어·한자·가나·태국 문자 등이 한 글자라도 섞이면 그 힌트는 **통째로 버린다.**
     일부만 지워 고쳐 쓰면 문장이 깨지므로 버리는 편이 낫다고 판단했다.
   - 검사는 정답을 `○` 로 가리기 **전에** 한다. `○` 는 화이트리스트에 없기 때문이다.
   - `cleanHints()` 를 새로 빼서 "몇 개가 살아남았는지"를 셀 수 있게 했다.
     `assemble()` 은 이 함수를 쓰도록 정리했다.

2. **재요청 — `parseQuizJson` 이 검사에 걸리면 실패로 돌린다**
   - 쓸 수 있는 힌트가 `QUIZ_LLM_HINT_MIN`(2개)에 못 미치면 `null` 을 돌려 재요청하게 했다.
     그냥 두면 확정 힌트 3개만 남아 매 판이 똑같아진다.
   - 012 에서 관측한 **카테고리 이름을 그대로 정답으로 내놓는 문제**(`직업` → `직업`)도
     여기서 걸러낸다. 이를 위해 `category` 를 인자로 받도록 바꿨다.
   - 검사가 깐깐해진 만큼 재요청 횟수를 2회 → `QUIZ_LLM_MAX_ATTEMPTS`(3회)로 늘렸다.
     모델이 올라가 있으면 한 번에 1초 남짓이라 부담이 작다.

3. **넉넉히 받기 — `QUIZ_LLM_HINT_REQUEST` 4 → 6**
   - 걸러질 몫을 감안해 더 받는다. 실제로 쓰는 것은 여전히 3개다.

4. **프롬프트 강화 (`buildPrompt`)**
   - "한글과 숫자만 쓰라"를 가장 중요한 규칙으로 못박고, 금지 예시(`big cat`, `FOOTBALL`, `圆形`)와
     대안(`빅캣`, `풋볼`)을 함께 줬다.
   - "지어낸 말 금지", "카테고리 이름 자체를 정답으로 쓰지 말 것"도 추가했다.

**검증**

Claude in Chrome 확장을 쓰지 않아서, 헤드리스 Chrome 으로 페이지를 실제로 띄우고
결과를 로컬 서버 접근 로그로 흘려보내 받았다.
(`--dump-dom` 은 비동기 작업이 끝나기를 기다려 주지 않아 이 방법을 썼다.)

1. **걸러내기 단위 확인 12건 — 12/12 통과.**
   실제로 관측했던 오염 사례를 그대로 넣었다.
   - 제거됨: `.big cat.`, `비ONGODB`, `圆形的球和脚用韩语怎么说?`, `jejik에 넣기도 합니다`,
     `소화 organs가 적은 동물`, ` FOOTBALL 이라는 외래어`, `หม`, 빈 문자열
   - 유지됨: `한국인들이 자주 먹는 빨간 과일`, `노루를 잡아먹을 수 있는 동물`,
     `1번은 막연한 힌트입니다.`, `크기가 큰 편이에요 (약 2미터)`
2. **정답 가리기** — `호랑이는 큰 고양이과 동물이에요` → `○○○는 큰 고양이과 동물이에요`
3. **실제 생성 6개 카테고리** — `qwen2.5:7b` 로 돌렸고 **한국어 아닌 글자가 하나도 나오지 않았다.**
   정답도 6개 모두 실재하는 낱말이고 카테고리 이름과 겹치지 않았다.

   | 카테고리 | 정답 | 소요 |
   |---|---|---|
   | 과일 | 복숭아 | 4.3초 |
   | 동물 | 호랑이 | 1.5초 |
   | 직업 | 의사 | 1.1초 |
   | 스포츠 | 축구 | 4.0초 |
   | 악기 | 가야금 | 3.9초 |
   | 나라 | 한국 | 1.1초 |

   수정 전 같은 조건에서는 4개 중 4개가 오염됐었다 (012 참고).

**남은 한계 — 힌트 내용의 정확도**

문자 오염은 사라졌지만 **내용이 틀린 힌트는 여전히 나온다.**
`복숭아` 에 "귤과 바나나 사이에", `호랑이` 에 "곰 중 가장 큰 것" 같은 식이다.
이건 7B 모델의 지식 한계라 걸러내기로는 잡을 수 없다.
확정 힌트 3개(글자 수·초성·첫 글자)가 항상 뒤에 붙으므로 문제를 풀 수는 있다.
더 개선하려면 더 큰 모델을 쓰거나, 정답을 내장 사전에서 고르고 힌트만 LLM 에 맡기는 방식을 검토해야 한다.

## 015 · 2026-08-29 · 정답은 내장 사전에서 고르는 방식으로 전환 + [연결 닫기] 버튼 추가

**요청한 내용**

> 더 손보려면 정답은 내장 사전에서 고르고 힌트만 LLM에 맡기는 방식으로 변경한다
> Llama 3.2연결 기능에 연결 확인처럼 연결닫기도 만들어줘

**AI가 한 일 — (1) 정답은 사전에서, 힌트만 LLM에서**

작은 모델이 낱말을 지어내거나(`무라부`) 카테고리 이름을 그대로 답으로 내놓는 실패를
**정답 선택을 모델에게서 빼앗아** 통째로 없앴다. 모델은 힌트 쓰기에만 집중한다.

1. `QuizContent` 에 두 함수를 추가했다.
   - `matchBuiltinCategory(input)` — 맞는 내장 카테고리가 없으면 **null 을 돌려준다.**
     기존 `findBuiltinCategory` 는 못 찾으면 아무거나 하나 골라 주는데,
     "정답을 사전에서 고를지 모델에게 맡길지" 를 가르는 기준으로는 쓸 수 없어서 따로 뺐다.
     `findBuiltinCategory` 는 이 함수를 쓰도록 정리했다.
   - `pickAnswer(category)` — 사전에서 `QUIZ_ANSWER_RE` 를 통과하는 낱말을 하나 고른다.
2. `LlamaClient` 에 힌트 전용 경로를 만들었다.
   `buildHintPrompt` / `parseHintsJson` / `requestHintsOnce` / `createHints`.
   정답을 프롬프트에 알려 주고 힌트만 JSON 으로 받는다.
3. `createQuiz` 를 갈래로 나눴다.
   - 내장 카테고리에 걸리면 → 사전에서 정답을 고르고 `createHints` 로 힌트만 받는다.
   - 사전에 없는 카테고리(사용자가 자유롭게 적은 것)는 → 기존 방식(`createQuizFromModel`)을 그대로 쓴다.
     이 갈래를 남겨 둔 이유는 사전에 없는 카테고리도 계속 지원하기 위해서다.
   - 힌트를 못 받으면 예외를 올려 호출부가 내장 사전 문제로 대체하게 뒀다.
4. 화면 문구를 실제 동작에 맞게 고쳤다.
   - 로딩: `'과일' 정답은 내장 사전에서 고르고, AI가 힌트를 만들고 있어요`
   - 결과: `Llama 3.2가 낸 문제였어요` → `AI가 힌트를 만든 문제였어요`
     (정답은 사전이 고르는 경우가 생겼으므로 두 갈래 모두에 맞는 말로 바꿨다)

**AI가 한 일 — (2) [연결 닫기] 버튼**

`LlamaClient.unload()` 와 `closeLlmConnection()` 을 만들고 [연결 확인] 옆에 버튼을 놓았다.
`keep_alive: 0` 으로 요청하면 Ollama 가 모델을 곧바로 내린다. 예열해 둔 `warmedModel` 도 함께 지운다.
예열한 모델은 30분 동안 램을 붙들고 있어서(7B 기준 약 4.4GB) 직접 돌려줄 수단이 필요했다.
서버가 이미 꺼져 있으면 내릴 것도 없으므로, 실패해도 "닫혔다"고 알리고 경고만 남긴다.

**AI가 한 일 — (3) 검증 중에 찾은 문제 두 가지**

- **모델이 힌트를 통째로 영어로 쓰는 문제.** `동물` 카테고리가 계속 실패했는데,
  원문을 보니 6개 전부 영어였다 (`WOODLAND ANIMAL`, `KING OF BEASTS`, `LARGE CAT`).
  걸러내기는 제대로 동작한 것이고 모델이 약한 쪽이었다. 설정을 바꿔 가며 실측해 대책을 골랐다.

  | 설정 | 여우 | 사자 | 호랑이 | 고양이 |
  |---|---|---|---|---|
  | 기존 (temp 0.9) | 2/6 | 1/6 | 1/1 | 1/1 |
  | temp 0.3 | 3/6 | 1/1 | 1/1 | 1/1 |
  | **temp 0.3 + 시스템 프롬프트 강화** | **3/6** | **3/6** | **6/6** | 1/2 |

  → 한글 전용 규칙을 **시스템 프롬프트에 절대 규칙으로** 옮기고(사용자 메시지에만 적으면 무시당했다),
    힌트 생성 온도를 `HINT_TEMPERATURE = 0.3` 으로 낮췄다.
    이 경로는 정답을 사전에서 무작위로 고르므로 다양성을 온도에 기댈 이유가 없다.
- **드물게 60초 타임아웃.** 모델이 JSON 을 끝내지 못하고 토큰을 계속 뽑아내는 경우가 있었다.
  두 요청 모두에 `num_predict: 400` 을 걸어 막았다.

**검증**

헤드리스 Chrome 으로 실제 페이지를 띄우고, 결과를 로컬 서버 접근 로그로 받아 확인했다.

1. **단위 확인** — `matchBuiltinCategory('과일')` → `과일`,
   없는 카테고리 → `null`, `pickAnswer` 가 고른 낱말이 실제 사전에 있는지 → true. 모두 통과.
2. **[연결 닫기]** — 예열 후 실제로 눌러 상태 문구를 확인했다.
   `🔌 연결을 닫았어요 — qwen2.5:7b 을(를) 메모리에서 내렸습니다.`
3. **내장 카테고리 8종 × 2회차 = 16번 — 15번 성공.**
   - 정답은 **16번 모두 내장 사전에서 나왔다** (`사전출처=true`).
   - 한국어가 아닌 글자는 **한 번도 나오지 않았다.**
   - 소요 시간 1.0~4.1초.
   - 실패한 1번(`채소` 2회차)은 힌트가 다 걸러진 경우로, 게임에서는 내장 사전 문제로 대체된다.
   - 고치기 전 같은 조건에서 `동물` 은 매번 실패했는데, 이번에는 두 회차 모두 성공했다.

**남은 한계** — 문자 오염과 정답 품질은 해결됐지만 **힌트 내용의 사실 정확도는 여전히 모델 몫이다.**
`늑대` 에 "고래보다 큰 동물", `포르투갈` 에 "레스토랑에서 증정하는 음료" 같은 힌트가 섞인다.
확정 힌트 3개(글자 수·초성·첫 글자)가 항상 붙으므로 문제는 풀 수 있다.

## 016 · 2026-08-29 · 버그 수정 — 스무고개가 설정한 횟수를 넘겨 계속 진행되던 문제

**요청한 내용**

> 스무고개 횟수를 설정했는데 적용이 안된다 횟수대로 진행하게 만들어줘

**원인**

`finishQuizSession()` 이 최종 결과 화면만 띄우고 **세션을 닫지 않았다.**
`QuizSession.reset()` 은 사용자가 결과창을 닫을 때(`closeQuizFinal`) 또는
다시 도전할 때(`restartQuizSession`)만 불린다.
그래서 마지막 라운드가 끝난 뒤에도 `QuizSession.active` 가 `true` 로 남아 있었고,
라운드를 여는 쪽(`openQuizRound` / `startQuizRound`)은 이 값만 보고 통과시키므로
정해 둔 횟수를 넘겨 계속 진행할 수 있었다.

5회로 설정하고 세션을 끝까지 돌려 추적한 기록이다.

```
라운드 5 시작됨 -> round=5/5
  다음라운드 후 -> active=true round=5      ← 여기서 끝났어야 한다
라운드 6 시작됨 -> round=5/5 정답=청포도
라운드 7 시작됨 -> round=5/5 정답=천도복숭아
최종 -> active=true history=7               ← 5회 설정인데 7판
```

**AI가 한 일**

1. `QuizSession.finish()` 를 추가했다. `active` 만 내리고 `history` 와 누적 점수는 남긴다.
   최종 결과 화면이 그 기록을 그대로 그리기 때문에 `reset()` 을 쓸 수 없었고,
   그래서 원래 코드가 세션 종료를 결과창 닫기까지 미뤄 둔 것으로 보인다. 둘을 분리했다.
2. `finishQuizSession()` 이 결과창을 만들기 **전에** `QuizSession.finish()` 를 부르게 했다.
3. `if (!QuizSession.active) return;` 가드를 앞에 붙여 결과창이 두 번 열리지 않게 했다.
   `그만하기`(`quizQuitBtn`)와 `cancelQuizSession()` 도 이 함수를 쓰므로 함께 안전해진다.

**검증**

헤드리스 Chrome 에서 실제 버튼 흐름 그대로(`startQuizSession` → `startQuizRound` →
`endGameByClear` → `nextQuizRound`) 세 가지 시나리오를 돌렸다.

1. **3회 설정** — 정확히 3라운드만 진행하고 종료했다.
   - 3라운드에서 버튼 라벨이 `최종 결과 보기` 로 바뀌었다.
   - 누른 뒤 `active=false`, 최종창 열림, 최종 문구 `3번 중 3번 맞혔어요`.
   - 4회차를 시도했으나 세션이 닫혀 있어 진행되지 않았다.
2. **종료 후 방어** — 최종창이 뜬 상태에서 `startQuizRound()` 를 억지로 불러도
   라운드가 열리지 않는다 (`QuizManager.active=false`).
3. **1회 설정** — 한 판만 진행했다. 첫 라운드부터 버튼이 `최종 결과 보기` 이고
   `그만하기` 는 감춰졌다. 종료 후 기록 수 1.

수정 전에는 같은 절차에서 5회 설정이 7판까지 이어졌다.

## 017 · 2026-08-29 · 버그 수정 — 제시어와 정답이 어긋나던 문제 (사전 검증 추가)

**요청한 내용**

> 스무고개 제시어와 답이 관련이 없는것이 나온다 제시어와 답이 연관되어 있는지 사전에서 검증해서 제시어와 답이 연관되게 만든다

**원인 — 두 군데였다**

1. **화면에 띄우는 제시어와 정답을 뽑은 곳이 서로 달랐다.**
   `beginQuizPlay()` 는 `GameState.currentCategory` 에 **사용자가 입력한 말**을 그대로 넣었다.
   그런데 AI 연결에 실패해 내장 사전으로 대체할 때 쓰는 `findBuiltinCategory()` 는
   맞는 카테고리를 못 찾으면 **아무 카테고리나 무작위로 골라** 정답을 뽑는다.
   그래서 "바다 생물" 이라고 적었는데 정답이 "회계사" 로 나오는 일이 생겼다.
   두 값이 애초에 이어져 있지 않았던 것이 근본 원인이다.
2. **부분 일치가 한 글자도 허용했다.** `matchBuiltinCategory('물')` 이 `동물` 에 걸렸다.

**AI가 한 일**

1. **제시어를 정답이 나온 카테고리에 맞췄다.**
   `beginQuizPlay(requestedCategory, quiz, ...)` 가 `quiz.category` 를 화면 제시어로 쓰도록 바꿨다.
   이러면 둘이 어긋날 수 있는 경로 자체가 사라진다.
   카테고리가 바뀐 경우에는 숨기지 않고 토스트로 알린다.
   `⚠ '바다 생물' 로는 문제를 만들지 못해 내장 사전의 '음식' 로 냈어요.`
2. **`QuizContent.answerFitsCategory(answer, category)` 를 추가했다.** (요청한 사전 검증)
   - 내장 카테고리면 → 반드시 그 카테고리 안에 있는 낱말이어야 한다.
   - 사전에 없는 카테고리(사용자가 자유롭게 적은 말)면 대조할 목록이 없으므로,
     대신 **다른 카테고리의 낱말은 아닌지**를 본다.
     '바다 생물' 이라고 했는데 직업 사전에 있는 '회계사' 가 나오면 거부한다.
   - 낱말이 어느 카테고리에 속하는지는 `categoriesOf(word)` 로 찾는다.
3. **모델이 정답까지 고르는 경로에 이 검증을 걸었다.** `parseQuizJson` 이 검증에 걸리면
   `null` 을 돌려 재요청한다 (015 에서 만든 재시도 흐름을 그대로 탄다).
4. **부분 일치는 두 글자부터만** 보도록 `matchBuiltinCategory` 를 고쳤다.

**검증** — 헤드리스 Chrome 에서 실제 흐름 그대로 돌렸다. 11개 항목 모두 통과.

1. **사전 검증 단위 확인**
   - `('사과','과일')` → true / `('회계사','과일')` → false
   - `('회계사','바다 생물')` → **false** (사전에 없는 제시어인데 다른 카테고리 낱말이라 거부)
   - `('고래','바다 생물')` → true (사전 어디에도 없는 낱말은 허용)
   - `matchBuiltinCategory('물')` → **null** (전에는 `동물` 이 잡혔다)
   - `matchBuiltinCategory('나라')` → `나라이름`
2. **AI 연결 실패 + 사전에 없는 제시어** — 입력 "바다 생물" → 화면 제시어 `음식`, 정답 `순댓국`.
   정답이 화면에 뜬 제시어의 사전에 실제로 들어 있는 것을 확인했다.
   고치기 전에는 제시어가 "바다 생물" 인 채로 정답만 엉뚱한 카테고리에서 나왔다.
3. **AI 연결 성공 + 내장 카테고리** — 제시어 `과일`, 정답 `애플망고` (과일 사전에 있음).

## 018 · 2026-08-29 · 정답을 항상 사전에서만 뽑도록 변경 (제시어-정답 카테고리 일치 보장)

**요청한 내용**

> 제시어와 정답이 같은 카테고리가 아닌거 같다 제시어와 정답이 같은 카테고르에 속해 있는지
> 사전데이터를 가져와서 비교해보고 정답이 제시어와 같은 카테고리에 있도록 해줘

**남아 있던 구멍**

017 에서 화면 제시어를 `quiz.category` 기준으로 바꿨지만, **사전에 없는 카테고리**는 여전히
모델이 정답까지 골랐다. 이 경로는 대조할 사전이 없어서 `answerFitsCategory` 도
"다른 카테고리의 낱말은 아닌지" 정도만 볼 수 있었다. 즉 모델이 엉뚱한 낱말을 지어내면
막을 방법이 없었다. 검증을 더 붙이는 대신 **정답을 지어낼 수 있는 경로 자체를 없앴다.**

**AI가 한 일**

1. **정답은 예외 없이 사전에서 고른다.** `createQuiz` 가 사전 매칭에 실패하면 문제를 만들지 않고
   `unknownCategory` 표시를 단 예외를 던진다. 모델에게는 힌트만 맡긴다.
2. **`offlineQuiz` 의 무작위 카테고리 대체를 없앴다.** 이것이 불일치의 뿌리였다.
   맞는 카테고리를 못 찾으면 `null` 을 돌려준다. `findBuiltinCategory()` 는 삭제했다.
3. **사전에 없는 카테고리는 되돌린다.** `startQuizRound` 가 문제를 받기 전에 먼저 확인하고,
   고를 수 있는 카테고리를 알려 준 뒤 **라운드를 소모하지 않고** 입력창을 그대로 둔다.
4. **판을 열기 직전에 한 번 더 대조한다.** `answerFitsCategory(quiz.answer, quiz.category)` 가
   어긋나면 사전 문제로 다시 만든다. 위에서 이미 사전에서 뽑으므로 통과해야 정상인 방어선이다.
5. **카테고리 입력창에 고를 수 있는 목록을 항상 표시한다.**
   파일로 추가한 카테고리도 `dictionary` 에 들어가므로 이 목록에 함께 나온다.
   기존 placeholder 가 `예: 과일, 바다 생물, 겨울 스포츠` 였는데, 사전에 없는 예시라 `예: 과일` 로 고쳤다.
6. **죽은 코드를 지웠다.** 정답까지 모델이 고르던
   `createQuizFromModel` / `parseQuizJson` / `buildPrompt` / `requestOnce` 를 삭제했다.

**검증** — 헤드리스 Chrome 에서 실제 흐름 그대로 돌렸다. 13개 항목 모두 통과.

3. **사전에 없는 카테고리** ("바다 생물") — 문제가 열리지 않고, 라운드도 소모하지 않고,

## 022 · 2026-08-29 · 카테고리를 세션 시작 때 한 번만 고르고 전 라운드에 적용

**요청한 내용**

> 스무고개 시작시 카테고리를 고르면 한번 정한 카테고리로 설정한 스무고개 횟수만큼 스무고개 게임을 한다

**바꾼 흐름**

- 전: 라운드마다 카테고리를 물었다 (007 에서 그렇게 만들었다).
- 후: **세션 시작 때 한 번만 묻고**, 그 카테고리로 정해진 횟수를 끝까지 진행한다.

**AI가 한 일**

1. `QuizSession` 에 `category` 를 추가했다. `start()` / `reset()` 에서 함께 비운다.
2. **`startQuizRound()` 를 둘로 나눴다.**
   - `startQuizRound()` — [문제 받기] 버튼. 입력한 카테고리를 검사하고
     `QuizSession.category` 로 굳힌 뒤 첫 판을 연다.
   - `runQuizRound(category)` — 라운드 한 판을 실제로 여는 곳. 카테고리를 인자로 받는다.
   블록 개수 검사는 매 라운드 필요하므로 `runQuizRound` 쪽으로 옮겼다.
3. `nextQuizRound()` 가 `openQuizRound()` 대신 `runQuizRound(QuizSession.category)` 를 부른다.
   즉 두 번째 라운드부터는 카테고리를 묻지 않는다.
4. `openQuizRound()` 는 남겨 두었다. **문제를 만들지 못했을 때 다른 카테고리로 다시 고를 수 있어야** 하기 때문이다.
   (사전에 없는 카테고리를 넣었거나, AI 실패 + 사전 대체까지 실패한 경우)
   이때 입력칸에는 이전에 고른 카테고리를 채우고 전체 선택해 둔다.
5. 문구를 흐름에 맞게 고쳤다.
   - 시작 모달: "라운드마다 새 카테고리를 입력하고" → "다음 화면에서 카테고리를 한 번 고르면 그 카테고리로 끝까지 진행하고"
   - 카테고리 화면 제목: `🗂 N라운드 카테고리` → `🗂 카테고리 정하기`
   - 카테고리 화면 설명: `N번 중 M번째예요...` → `여기서 고른 카테고리로 N번 모두 진행해요.`

**검증**

헤드리스 Chrome 에서 4회 세션을 실제 버튼 흐름 그대로 돌렸다. 모두 통과.

- 카테고리 화면 제목/설명이 새 문구로 나온다.
- `QuizSession.category` 에 `악기` 가 저장된다.
- **4판 모두 `악기` 로 진행됐다.** 정답은 판마다 달랐다 (소고 → 아코디언 → 장구 → 하프).
- **두 번째 라운드부터 카테고리를 다시 물은 횟수 0회.**
- 4라운드 뒤 세션이 끝나고 최종 결과창에 `4번 중 4번 맞혔어요` 가 떴다 (016 의 종료 처리도 그대로 동작).
- 사전에 없는 카테고리(`바다 괴물`)를 넣으면 여전히 문제가 열리지 않고 입력창이 유지되며,
  `QuizSession.category` 도 비어 있는 채로 남는다 (018 의 방어가 그대로 동작).

검증 도중 하네스가 비동기 라운드 생성을 700ms 만 기다려 2라운드부터 실패로 찍힌 적이 있다.
`nextQuizRound` 가 `runQuizRound` 를 await 없이 부르므로, 조건 대기(`waitFor`)로 고쳐 다시 확인했다.
게임 코드 문제는 아니었다.

## 023 · 2026-08-29 · 문제 생성 대기 시간 단축 — 다음 판 미리 만들기

**요청한 내용**

> 스무고개  만드는 중 시간이 오래걸린다 시간을 단축시켜줘

**먼저 어디서 시간이 쓰이는지 쟀다**

Ollama 의 응답에 들어 있는 `total_duration` / `prompt_eval_duration` / `eval_duration` 을 뜯어 봤다.

| 카테고리 | 총 시간 | 모델 로드 | 프롬프트 처리 | 실제 생성 |
|---|---|---|---|---|
| 과일 | 1.37초 | 0.03초 | 0.34초 (388토큰) | 0.98초 (40토큰) |
| 악기 | 1.31초 | 0.00초 | 0.31초 | 0.98초 (39토큰) |
| 날씨 | 2.46초 | 0.00초 | 0.31초 | 2.05초 (78토큰) |
| 직업 | 1.04초 | 0.00초 | 0.32초 | 0.62초 (25토큰) |

`ollama ps` 로 확인하니 **100% GPU** 로 돌고 있고 생성 속도는 40 tok/s 였다.
즉 **모델이 느린 게 아니었다.** 한 번 요청은 1~2.5초면 끝난다.

느리게 느껴지는 진짜 이유는 세 가지였다.

1. 매 라운드마다 **순서대로 기다린다.** 판이 끝나면 그때부터 다음 문제를 만들기 시작한다.
2. 힌트가 걸러지면 **최대 3번 재요청**하므로 그만큼 배로 늘어난다.
3. `[연결 확인]` 을 누르지 않고 시작하면 첫 판이 **콜드 로드(수십 초)** 를 그대로 뒤집어쓴다.

**AI가 한 일**

1. **다음 판을 미리 만들어 둔다 (프리페치).**
   022 에서 카테고리가 세션 내내 같아졌기 때문에 가능해진 방법이다.
   `QuizSession` 에 `prefetch` / `prefetchCategory` 를 두고
   `startPrefetch()` / `takePrefetch()` / `clearPrefetch()` 를 만들었다.
   - 판이 시작된 직후(`beginQuizPlay` 뒤)에 다음 판 문제를 백그라운드로 요청한다.
   - 마지막 판이면 미리 받지 않는다. 이미 받는 중이면 중복 요청하지 않는다.
   - 꺼낼 때 **카테고리가 다르면 쓰지 않는다.**
   - 미리 받다가 실패하면 조용히 `null` 이 되고, 쓸 때가 되면 그 자리에서 다시 요청한다.
     즉 프리페치가 실패해도 예전과 같은 동작으로 돌아갈 뿐 나빠지지 않는다.
   - 세션 시작·종료·초기화(`start` / `finish` / `reset`)에서 함께 정리된다.
2. **로딩 화면을 200ms 뒤에만 띄운다** (`QUIZ_LOADING_DELAY`).
   미리 만들어 둔 판은 즉시 시작되는데 로딩 화면이 뜨면 화면만 깜빡인다.
3. **세션 시작 때 모델을 예열한다.** `startQuizSession()` 에서 `warmUp()` 을 기다리지 않고 던져 둔다.
   사용자가 카테고리를 고르는 동안 모델이 올라가므로, `[연결 확인]` 을 누르지 않고 바로 시작해도
   첫 판이 콜드 로드를 그대로 맞지 않는다.

**검증** — 4라운드 세션을 두 가지 조건으로 돌려 라운드 시작 대기 시간을 쟀다.

|---|---|---|---|---|---|

- `그만하기`(`stopGame`) 를 누르면 미리 받던 것도 정리되는 것을 확인했다.

**남은 것** — **1라운드는 여전히 1~3초 걸린다.** 카테고리를 입력받기 전에는 무엇을 만들지 알 수 없어
미리 만들 수가 없다. 예열을 앞당겨 콜드 로드는 피했지만 생성 자체는 그 자리에서 해야 한다.

## 024 · 2026-08-29 · 모드 1 정답 목록을 한 판 마친 뒤에만 열 수 있게 변경

**바꾼 규칙**

**AI가 한 일**

1. `GameState` 에 `answerListUnlocked` 플래그를 추가했다 (처음에는 `false`).
2. `finishGame()` 에서 판이 끝나면 `true` 로 바꾼다. 모드 2 는 정답 목록을 쓰지 않으므로 제외했다.
   `resetForGameEnd()` 는 이 값을 건드리지 않으므로, 한 번 마치면 그 세션 동안 유지된다.
3. **제시어 카드 문구를 세 갈래로 나눴다.**
   - 진행 중: `🔒 게임 중에는 볼 수 없어요`
   - 아직 못 마쳤을 때: `🔒 게임이 끝나면 볼 수 있어요`
   - 마친 뒤: `👀 눌러서 정답 보기`
   잠김 표시(`locked` 클래스)와 툴팁도 같은 기준으로 맞췄다.
4. `openAnswerList()` 에 잠금 검사를 추가했다.
   눌러도 열리지 않고 `정답 목록은 한 판을 마친 뒤에 볼 수 있어요!` 토스트를 띄운다.
5. HTML 의 초기 문구도 잠긴 상태(`🔒 게임이 끝나면 볼 수 있어요`)로 바꿨다.
   예전에는 첫 화면부터 `👀 눌러서 정답 보기` 로 떠 있었다.

**검증** — 헤드리스 Chrome 에서 실제 흐름 그대로 돌렸다. 11개 항목 모두 통과.

1. **한 번도 안 했을 때** — 문구 `🔒 게임이 끝나면 볼 수 있어요`, 카드 잠김,
   눌러도 정답 목록이 열리지 않는다.
2. **진행 중** — 문구 `🔒 게임 중에는 볼 수 없어요`, 눌러도 열리지 않는다.
3. **끝난 뒤** — 잠금이 풀리고 문구가 `👀 눌러서 정답 보기` 로 바뀌며,

4. **새 판을 시작하면** 다시 `🔒 게임 중에는 볼 수 없어요` 로 잠기고 열리지 않는다.

**알아 둘 점** — 한 판을 마치면 그 뒤로는 게임을 하지 않는 동안 계속 열 수 있다.
다시 시작하면 진행 중에는 물론 잠긴다. 매번 새로 잠그려면 판을 시작할 때 플래그를 내리면 된다.

## 027 · 2026-08-30 · 버그 수정 — [연결 닫기]를 눌러도 모델이 메모리에 다시 올라오던 문제

**요청한 내용**

> 스무고개 llm 연결닫기시 연결닫기 버튼이 제대로 작동하지 않는데 제대로 연결닫기가 되도록 만든다

**AI가 한 일**

1. **원인을 먼저 재현했다.** [연결 닫기]는 `LlamaClient.unload()` 로 `keep_alive: 0` 요청 한 번만
   보내고 있었다. 요청 자체는 정상이라 `/api/ps` 가 잠깐 비긴 하는데, **판을 푸는 동안 다음 문제를
   미리 받아 두는 요청(023에서 넣은 `QuizSession.startPrefetch`)이 아직 돌고 있다가 뒤늦게 끝나면서
   `keep_alive: '30m'` 으로 모델을 다시 메모리에 올려 버렸다.** 화면에는 "메모리에서 내렸습니다"라고
   떠 있는데 실제로는 4.4GB가 그대로 남아 있는 상태였다.

2. **`LlamaClient` 에 요청 관리 기능을 넣었다.**
   - `inflight` — 진행 중인 `AbortController` 를 모아 둔다. `fetchWithTimeout` 이 등록·해제한다.
   - `abortAll()` — 돌고 있는 요청을 모두 끊고, `closed` 표시를 세워 새 요청도 막는다.
   - `reopen()` — 다시 연결할 때 잠금을 푼다. `ensureLlmReady()` 첫 줄에서 부른다.
   - `isLoaded()` — `/api/ps` 로 **모델이 정말 내려갔는지 확인한다.** 기존 `ping()` 은 `/api/tags`(설치
     목록)만 봐서 메모리에 올라가 있는지는 알 수 없었다.
   - `requestHintsOnce()` 앞에 `closed` 검사를 넣어, 닫은 뒤에는 미리 받기가 모델을 다시 올리지 못하게 했다.

3. **`closeLlmConnection()` 의 순서를 바로잡았다.**
   ① 진행 중인 요청 끊기 → ② `QuizSession.clearPrefetch()` 로 미리 받아 둔 문제 버리기 →
   ③ 모델 내리기 → ④ `/api/ps` 로 확인, 아직 남아 있으면 0.8초 뒤 한 번 더 내리기.
   확인까지 통과해야 "내린 것을 확인했어요"라고 말하고, 그래도 남아 있으면 성공했다고 하지 않고
   다시 눌러 달라고 안내한다. **되지도 않은 일을 됐다고 말하던 것이 이 버그의 핵심이었다.**

4. **곁가지도 함께 정리했다.** 버튼에 `id="llmCloseBtn"` 을 주고 닫는 동안 비활성화해 중복 클릭을 막았다.
   예열 도중에 [연결 닫기]를 누르면 예열 쪽 문구("✅ 연결됨…")가 닫기 안내를 덮어쓰던 것도 막았다.
   `unload()` 대기 시간은 32초 → 60초로 늘리고(다른 요청이 끝날 때까지 서버에서 기다릴 수 있다),
   `warmUp()`/`unload()` 가 응답 본문을 읽지 않고 버려 연결이 열린 채 남던 것도 고쳤다.

**검증** — Ollama(qwen2.5:7b)를 실제로 띄우고, 게임 화면을 headless Edge로 열어 **수정 전/후를 같은
시나리오로 돌려 비교했다.** 시나리오는 "예열 → 미리 받기 요청이 도는 중에 [연결 닫기]".

| | 수정 전 | 수정 후 |
|---|---|---|
| 화면 문구 | 🔌 …메모리에서 내렸습니다. | 🔌 …내린 것을 확인했어요. (진행 중이던 요청 1건도 취소했어요) |
| 닫은 직후 `/api/ps` | `[]` | `[]` |
| **8초 뒤 `/api/ps`** | **`["qwen2.5:7b"]` ← 되살아남** | **`[]` ← 그대로 내려가 있음** |

이어서 닫은 뒤 `createQuiz()` 호출이 막히는 것, [연결 확인]으로 다시 연결하면 정상적으로 올라오는 것

## 028 · 2026-08-30 · 게임 진입 전 시작 화면 추가 — 혼자 하기 / 멀티플레이 고르기

   - 멀티플레이 화면 위쪽에 `[← 처음 화면]` 을 넣었다. 시작 화면이 붙여 주는 `?from=start` 가
     있을 때만 보인다(주소창으로 바로 들어온 사람에게는 돌아갈 곳이 없다).
     **링크가 아니라 뒤로 가기를 쓴 이유**: 시작 화면은 파일(`file://`)로 열려 있을 수 있는데,
     http 페이지에서 `file://` 로 이동하는 것은 브라우저가 막는다. 뒤로 가기는 허용된다.

**검증** — 정적 서버(8777)에 게임을, 3000번에 멀티플레이 화면을 띄우고 headless Edge로 확인했다.
(이 PC에는 node가 없어 멀티플레이 서버는 `/healthz` 와 화면만 흉내 내는 대역을 썼다.)

|---|---|
| 첫 화면이 시작 화면인가 / 멀티 칸은 접혀 있나 | 표시됨 / 접힘 |
| 서버 켜짐·꺼짐을 구분해 알리는가 | "✅ 서버가 켜져 있어요" / "⚠ 서버 응답이 없어요" |

| [🏠 처음 화면] → 판 정리 후 복귀 | 시작 화면 복귀, 보드 0개로 정리 |
| [접속하기] → 멀티플레이 이동 (`127.0.0.1:3000` 처럼 짧게 입력) | 로비 도착, `[← 처음 화면]` 노출 |

## 029 · 2026-08-30 · 멀티플레이 서버 실행 환경 마련 — 포터블 Node + `서버 켜기.bat`

**요청한 내용**

> 멀티플레이 서버에 접속에서 접속하기 버튼을 클릭하면 접속되지 않는다 서버를 켜는 방법을 알려줬는데 해당 명령어가 실행 되지 않는다 서버에 접속할 수 있도록 구현한다

**AI가 한 일**

0. **원인부터 확인했다.** 서버 코드(`server/`)에는 문제가 없었다. 진짜 원인은 **이 PC에
   Node.js도 Docker도 설치돼 있지 않다**는 것이었다. 시작 화면이 안내하던
   `docker compose up --build` / `npm install && npm start` 가 둘 다 "명령을 찾을 수 없음"으로
   끝나니 서버가 뜨지 않았고, 서버가 없으니 [접속하기]도 실패한 것이다.
   (`where node/npm/docker` 모두 없음, `node_modules` 도 없음. Python 3.13 은 설치돼 있었다.)

1. **포터블 Node.js 를 프로젝트 안에 넣었다** (`tools/node/`).
   사용자가 "관리자 권한 없이, 기존 서버 코드를 그대로 쓰는 방식"을 골랐기 때문이다.
   nodejs.org 공식 `node-v24.20.0-win-x64.zip` 을 받아 **SHA256 체크섬을 대조해 확인한 뒤**
   `tools/node/` 로 풀었다. 시스템 PATH나 레지스트리를 건드리지 않으므로, 지우고 싶으면
   폴더만 삭제하면 된다. 이어서 `server/` 에 `npm install` 로 의존성 90개를 설치했다.

2. **`서버 켜기.bat` 을 프로젝트 루트에 만들었다.** 이번 문제의 핵심이 "명령어를 칠 수 없다"는
   것이었으므로, **더블클릭 한 번**으로 끝나게 했다. 이 파일이 하는 일은
   ① `tools/node` 를 찾아 PATH 앞에 붙이고(없으면 PC에 설치된 node 를 쓰고, 그것도 없으면
   내려받는 방법을 한국어로 안내하고 멈춘다), ② `node_modules` 가 없으면 `npm install` 을
   먼저 돌리고, ③ 서버를 켠 뒤 브라우저로 `http://localhost:3000` 을 열어 준다.
   콘솔 코드페이지가 949라 Node 의 UTF-8 출력이 깨지므로 맨 위에 `chcp 65001` 을 두고
   배치 파일 자체도 UTF-8(CRLF)로 저장했다.

3. **서버가 켜질 때 접속 주소를 직접 알려주도록 했다** (`server/src/server.js`).
   `os.networkInterfaces()` 로 내부용이 아닌 IPv4 주소를 모아, `이 PC에서는 http://localhost:3000`
   과 `같은 인터넷의 PC는 http://192.168.x.x:3000` 을 함께 출력한다.
   친구가 접속할 때 IP를 따로 찾아보지 않아도 되게 하기 위해서다.

4. **화면과 문서의 안내를 실제로 되는 방법으로 고쳤다.**
   - `word_connection_game_v2.html` 시작 화면의 "서버를 켜는 방법" 칸에서 docker/npm 명령어를
     빼고 `[서버 켜기.bat] 더블클릭` + 다른 PC에서 참가하는 법으로 바꿨다(`.guide-steps` 추가).
   - `server/README.md` 맨 앞에 포터블 Node 방식 설명과, `tools/node` 가 없을 때 다시 받는
     방법을 넣었다. Docker 방식 설명은 그대로 뒀다.
   - `.gitignore` 를 새로 만들어 `tools/` 와 `node_modules/` 를 저장소에서 제외했다
     (Node 런타임 37MB를 커밋하지 않기 위해서다).

**검증** — 실제로 서버를 띄우고 소켓까지 확인했다.

| 확인한 것 | 결과 |

| Node zip 무결성 (SHA256 vs 공식 SHASUMS256.txt) | 일치 |

| `서버 켜기.bat` 더블클릭 실행 | 서버 기동, 한글 안내문 깨짐 없이 출력 |

검증 후 테스트로 띄운 서버는 종료해 두었다. 실제 플레이 시에는 `서버 켜기.bat` 을 실행하면 된다.


## 030 · 2026-08-30 · 버그 수정 — 파일로 직접 열면 [방 만들기]·[참가하기] 가 먹통이던 문제

**요청한 내용**

> sever에 index.html에서 방만들기와 참가하기 버튼이 실행이 안된다 실행이 되도록 만들어줘

**AI가 한 일**

1. **크롬(puppeteer)으로 두 가지 방법으로 열어 재현했다.** 결과가 갈렸다.

   | 여는 방법 | `io` 로드 | [방 만들기] |
   |---|---|---|
   | `http://localhost:3000` | function | 방 코드 발급 + 대기실 진입 (정상) |
   | `public/index.html` 직접 열기 (`file://`) | undefined | 무반응 |

2. **원인**: 파일로 열면 `<script src="/socket.io/socket.io.js">` 가
   `file:///D:/socket.io/socket.io.js` 로 해석돼 404가 난다. 그러면 그 아래 스크립트가
   첫 줄 `const socket = io();` 에서 `io is not defined` 로 죽고, **그 블록 전체가 중단**된다.
   버튼 이벤트 연결(`addEventListener`)이 그 아래에 있어서 하나도 등록되지 않았고,
   그래서 눌러도 아무 일이 없었다. 서버·버튼 코드 자체에는 문제가 없었다.

3. **고친 방법** (`server/public/index.html`) — 원인을 화면에서 바로 알 수 있게 했다.
   메인 스크립트 맨 앞에 부팅 점검을 두어 `typeof io === 'undefined'` 이면
   화면 전체를 덮는 안내(`#bootError`)를 띄우고 곧바로 `throw` 로 멈춘다.
   안내에는 ① `서버 켜기.bat` 실행 ② `http://localhost:3000` 으로 다시 열기 순서와
   바로 이동하는 단추를 넣었다. 파일로 연 경우와 서버 응답이 없는 경우의 문구를 다르게 했다.
   덤으로 `favicon.ico` 404를 없애려 인라인 SVG 아이콘을 넣었다.

**검증** — 크롬 자동화로 두 경우를 다시 확인했다.
`http://localhost:3000` → 안내 안 뜸, [방 만들기] 정상(방 코드 N5DZ), 콘솔 오류 0건.
`file://` → 안내 뜸("index.html 파일을 직접 열어서…"), 의도한 `throw` 외 다른 오류 없음.

## 031 · 2026-08-30 · 멀티플레이 목표 글자 수 제거 + 게임 시간 설정 추가

**요청한 내용**

> 단어 연결 게임 - 멀티플레이 에서 목표글자수 항목은 제거하고 게임 시간을 설정할수 있게 한다

**AI가 한 일**

1. **목표 글자 수 설정을 없앴다.** 화면(`server/public/index.html`)에서 입력칸을 빼고,
   서버의 `settings.wordLength` 와 검증 로직(`MIN/MAX_WORD_LENGTH`)도 함께 지웠다.
   - 길이는 이제 **서버가 라운드마다 고른다**. `createRound()` 는 블록 안에 들어가는
     그 카테고리 단어 중 무작위로 2개를 뽑으므로 `애플망고`(4글자) + `자두`(2글자) 처럼
     길이가 서로 달라도 된다.
   - **정답 규칙도 함께 바꿨다.** 길이 힌트가 사라진 만큼, 혼자 하기 모드와 같은 기준
     (보드 글자로 만들 수 있고 그 카테고리의 단어이면 정답)으로 맞췄다.
     `Round.isAcceptableWord()` 를 새로 두어 사전 조회 + 보드 글자 다중집합 포함 검사를 한다.
     보드에 심는 목표 단어 2개는 "적어도 두 개는 반드시 만들 수 있다"를 보장하는 장치로 남겼다.
   - 클라이언트에 있던 `blocks.length !== wordLength` 즉시 반려도 없앴다(두 글자 미만만 막는다).

2. **게임 시간을 방장이 정하게 했다.** 60초 고정이던 값을 설정으로 뺐다.
   - `Room.settings.durationSeconds` 추가(기본 60초), 허용 범위 30~300초를
     `MIN/MAX_GAME_DURATION_SECONDS` 로 도메인에 뒀다.
   - `RoundService._beginGame()` 이 `room.timeLeft` 를 이 값으로 맞추고,
     `game:started` 이벤트로 `durationSeconds` 를 함께 보내 모두의 타이머가 같은 값에서 시작한다.
   - 화면에는 30 / 60 / 90 / 120 / 180 / 300초 선택칸(`#durationInput`)을 넣었다.
     숫자 입력칸 대신 고른 값만 받는 select 로 둬서 이상한 값이 들어갈 여지를 줄였다.

3. **문서 갱신** — `server/README.md` 의 게임 방법에서 목표 글자 수를 게임 시간으로 바꾸고,
   "글자 수 제한 없음" 정답 규칙 절을 추가했다.

## 032 · 2026-08-30 · 멀티플레이 [게임에서 나가기] 버튼 + 카테고리 8종 → 20종 증설

**요청한 내용**

> 단어 연결 게임 - 멀티플레이 에서 처음화면(혼자/멀티 고르기)버튼을 누루면 게임에서 나가기로 만들고 멜티게임의 카테고리를 혼자하기에 제시어 맞추기 카테고리에 있는거 만큼 증설해준다

**AI가 한 일**

1. **[← 처음 화면] 을 [🚪 게임에서 나가기] 로 바꿨다** (`server/public/index.html`).
   예전 버튼은 `window.history.back()` 으로 **화면만** 되돌렸다. 방에서 나간 것인지가 분명하지 않았다.
   지금은 순서를 바꿔서, 소켓을 먼저 끊어 **방에서 확실히 빠져나온 뒤** 화면을 옮긴다.
   - `NetworkManager.disconnect()` 를 추가했다. 서버는 disconnect로 이탈을 처리하므로(Design §6.2)
     남은 사람의 참가자 목록·순위표가 곧바로 갱신되고, 방장이 나가면 다음 사람에게 방장이 넘어간다.
   - 실수로 누르는 일을 막으려고 확인창을 둔다. 게임 중이면 "지금까지 얻은 점수는 사라집니다"라고 알린다.
   - 노출 조건을 바꿨다. 예전에는 `?from=start` 로 들어왔을 때만 보였는데,
     이제 **방에 들어간 뒤부터**(대기실·게임·게임오버) 보인다. 로비에는 나갈 게임이 없기 때문이다.
   - 나간 뒤 갈 곳: 시작 화면에서 왔으면 뒤로 가기로 그 화면으로, 주소창으로 바로 들어왔으면
     새로고침해 이 서버의 로비로 되돌린다. **되돌아갈 기록이 없을 때** 연결만 끊긴 화면에 갇히는 일이
     있어서, 뒤로 가기가 아무 일도 하지 않으면 0.4초 뒤 새로고침하는 대비책을 넣었다.

2. **카테고리를 8종 → 20종으로 늘렸다.**
   `word_connection_game_v2.html`(혼자 하기 — 제시어 맞추기)의 사전을 그대로
   `server/src/domain/dictionary.js` 로 옮겼다. 특허용어 · 색깔 · 악기 · 교통수단 · 곤충 · 바다생물 ·
   꽃 · 가전제품 · 학용품 · 신체부위 · 날씨 · 가구 12종이 더해져 총 **20종 406단어**가 되었다.

3. **같은 목록을 두 곳에 두지 않게 했다.**
   원래 클라이언트에도 카테고리 배열이 복사돼 있어서, 서버 사전만 늘리면 화면에는 안 나왔다.
   이번 증설이 딱 그 함정이라 목록을 서버 한쪽으로 모았다.
   `RoomService` 가 `room:create` / `room:join` 응답에 `categories` 를 함께 실어 보내고,
   클라이언트는 방에 들어간 시점에 그 목록으로 선택칸을 채운다(`populateCategorySelect`).

## 033 · 2026-08-30 · 멀티플레이에 AI 스무고개 모드 추가 (게임 종류 고르기)

**요청한 내용**

> 단어 연결 게임 - 멀티플레이에서 제시어 맞추기랑 AI스무고개를 선택해서 게임을 할 수 있도록 구현해줘

**AI가 한 일**

0. **가장 중요한 설계 판단: LLM 을 누가 부르는가.**
   혼자 하기 모드는 브라우저가 직접 Ollama 를 불렀지만, 멀티플레이에서는 **서버가 부른다**.
   두 가지 이유 때문이다. ① 정답이 서버 밖으로 나가면 안 된다(Design §1.2).
   ② 모두가 **같은 힌트를 같은 순서로** 봐야 공정하다 — 각자 부르면 힌트가 제각각이 된다.

1. **도메인 계층** — I/O 없는 규칙만 담았다.
   - `quizContent.js`: 혼자 하기의 `QuizContent` 를 옮겼다. 힌트 다듬기(한국어 아닌 글자가 섞이면
     통째로 버림), 정답 가리기(○○), 확정 힌트 3개(글자 수·초성·첫 글자), 사전에서 정답 뽑기.
   - `QuizRound.js`: 한 라운드의 상태. 힌트를 하나씩 여는 `revealNextHint()` 와,
     단어 연결의 `Round` 와 같은 방식으로 "먼저 맞힌 한 명만" 을 보장하는 `solved` 플래그를 둔다.
     `toClientPayload()` 는 정답과 아직 안 연 힌트를 빼고 내보낸다.

2. **인프라 계층** — `OllamaHintGenerator.js`.
   혼자 하기에서 검증된 프롬프트·시스템 규칙·온도(0.3)·`format:'json'`·`num_predict:400` 을 그대로 옮겼다.
   `ping()` / `warmUp()` / `generateHints()` 세 가지만 노출한다.

3. **응용 계층** — `QuizService.js`. `RoundService` 와 나란한 위치다. 다른 점은 두 가지뿐이다.
   끝나는 조건이 시간이 아니라 **문제 수**이고, 문제를 만들 때 LLM 이 필요하다는 것.
   - 1초짜리 타이머 하나가 남은 시간과 힌트 공개(10초마다)를 함께 몬다.
   - **정답은 언제나 사전에서 고른다.** LLM 에는 힌트만 맡긴다(혼자 하기 018과 같은 이유).
   - **다음 문제를 미리 만들어 둔다.** 이번 판을 푸는 동안 만들어 두면 라운드 사이 기다림이 없다.
     실제로 1라운드는 167초 걸렸지만 2라운드부터는 즉시 시작됐다.
   - **AI 가 꺼져 있어도 게임이 멈추지 않는다.** 힌트 생성이 실패하면 확정 힌트만으로 진행한다.

4. **소켓 계약** — 이벤트 이름을 늘리지 않고 방의 모드로 갈랐다.
   `game:start` 에 `mode` 가 붙고, `answer:submit`·`game:restart` 는 방의 모드를 보고
   `RoundService` / `QuizService` 로 갈라진다. 스무고개 전용으로는
   `quiz:preparing` · `quiz:round:started` · `quiz:hint` · `quiz:round:result` 와,
   대기실에서 AI 상태를 묻는 `ai:status` 를 더했다.

5. **화면** (`server/public/index.html`)
   - 대기실에 **게임 종류 고르기** 카드 2장을 넣고, 고른 것에 따라 설정 칸이 바뀌게 했다.
   - 스무고개 화면(`#screen-quiz`)을 새로 만들었다 — 카테고리/남은 시간/문제 번호 카드,
     힌트가 하나씩 쌓이는 목록, 정답 입력칸, 실시간 순위.
   - 정답 효과(꽃가루·뜨는 글자)가 보드 기준으로만 떠서 스무고개 화면에서는 보이지 않았다.
     기준 칸을 모드에 따라 고르도록 `effectHost()` 를 뒀다.

6. **첫 문제 대기 시간 문제를 고쳤다.**
   처음 구현에서는 첫 문제까지 **167초**가 걸렸다(모델 콜드 로드). 두 가지로 줄였다.
   ① 방장이 대기실에서 스무고개를 고르는 순간(`ai:status`) 서버가 모델을 미리 올린다.
   ② `game:start` 응답을 첫 문제 완성까지 붙들지 않는다 — 화면은 이미 "만드는 중" 으로 넘어가 있다.
   예열된 상태에서는 시작 후 **2초** 만에 1라운드가 열렸다.

**검증** — 소켓 종단 테스트와 브라우저(탭 2개) 테스트를 모두 돌렸다.

## 034 · 2026-08-30 · 멀티플레이 스무고개를 혼자 하기 모드 2와 같은 방식·화면으로 통일

**요청한 내용**

> 단어 연결게임 - 멀티플레이 AI 스무고개 정답을 맞추는 방법은 혼자하기에 모드2 AI 스무고개와같은 방식으로 구성해주고 화면 디자인도 똑같은 방식으로 맞춰줘

**AI가 한 일**

먼저 혼자 하기 모드 2가 실제로 어떤 방식인지 확인했다. **정답을 입력창에 적는 것이 아니라
보드에서 블록을 이어 만들고**, 보드 오른쪽에 힌트 패널(`#hintPanel`)이 붙으며,
점수는 **본 힌트가 적을수록 높다**(`max(1, 힌트수 + 1 - 본 힌트수)`). 직전 구현(033)은
정답을 입력창에 타이핑하는 방식이라 조작도 화면도 달랐다. 이를 맞췄다.

1. **정답을 맞히는 방식을 보드 드래그로 바꿨다.**
   - `quizContent.buildQuizBoard()` 를 추가했다. 혼자 하기와 같은 방식으로 정답 글자를 먼저 넣고
     남는 칸을 흔한 음절로 채운 뒤 섞는다. 정답을 블록으로 만들어야 하므로 정답 글자가 반드시 보드에 있다.
   - `pickAnswer()` 가 블록 개수를 받아 **보드보다 긴 낱말은 빼고** 고르게 했다.
   - `QuizRound` 에 `board` 를 넣고 `quiz:round:started` 로 함께 보낸다.
   - 클라이언트의 정답 입력창을 없앴다. 이제 `GameController.finishConnect` 가 두 모드의 제출을
     모두 처리한다(서버가 방의 모드를 보고 갈라 주므로 이벤트는 `answer:submit` 하나 그대로다).

2. **점수를 혼자 하기와 같은 계산으로 바꿨다.**
   `QuizRound.points()` = `max(1, 힌트수 + 1 - 본 힌트수)`. 힌트 1개만 보고 맞히면 6점,
   6개를 다 보고 맞히면 1점이다. 먼저 맞힌 한 명만 얻는 규칙은 그대로다.

3. **화면을 혼자 하기와 같은 구성으로 다시 짰다.**
   - 스무고개 전용 화면(`#screen-quiz`)을 없애고 **게임 화면 하나를 두 모드가 함께 쓰게** 했다.
     혼자 하기가 그렇게 되어 있고, 두 모드 모두 같은 보드를 쓰기 때문이다.
   - 보드 컨테이너 안에 `<aside id="hintPanel">` 을 넣고, 스무고개일 때만
     `#board-container.quiz-mode` 로 펼친다. 패널 구성(제목 `🤖 스무고개 1/3`,
     `다음 힌트 N초` 배지, 힌트 목록, 아래 안내줄)과 CSS를 혼자 하기에서 그대로 옮겼다.
   - 모드별 규칙 배너를 위에 뒀다(제시어=노란색 / 스무고개=보라색).
   - `body.quiz-layout` 으로 화면 폭을 1020px 로 넓힌다. 게임 화면을 벗어나면 되돌린다.
   - 블록 개수 설정을 두 모드가 함께 쓰는 공통 칸으로 옮겼다(스무고개도 보드를 쓰므로).
   - 정답 연출이 두 번 터지지 않게, 스무고개에서는 축하 연출을 `quiz:round:result` 쪽에만 맡겼다.

4. **`다음 힌트 N초` 는 서버 시계를 따르게 했다.**
   클라이언트가 따로 세면 어긋나므로, `game:tick` 에 `nextHintIn` 을 실어 보낸다.

**검증** — 브라우저(탭 2개)로 실제 드래그까지 확인했다.

## 035 · 2026-08-30 · 멀티플레이에 게임 배경 고르기 추가

**요청한 내용**

> 단어 연결 게임 - 멀티플레이에서 혼자하기 게임배경을 설정할 수 있는 것처럼 하도록 구현해줘

**AI가 한 일**

0. **판단 하나를 먼저 정했다 — 배경은 누구의 것인가.**
   혼자 하기에서 배경은 "내가 보는 화면"의 취향이다. 그래서 멀티플레이에서도
   **방 전체가 아니라 사람마다 따로** 고르게 했다. 방장이 정해 모두에게 강요하지 않는다.
   덕분에 서버·소켓 계약은 전혀 건드리지 않았고, 고른 값은 그 브라우저에만 기억해 둔다.
   (방 전체가 같은 배경을 쓰는 편이 나으면 서버 설정으로 옮길 수 있다.)

1. **그림을 서버가 서빙할 수 있게 옮겼다.**
   `배경1~4.png` 와 `assets/thumb-bg1~4.png` 를 `server/public/assets/` 로 복사했다.
   파일 이름은 `bg1~4.png` / `thumb-bg1~4.png` 로 바꿨다 — 한글 파일명은 URL 인코딩을 타기 때문에
   서버로 서빙할 때는 영문 이름이 문제가 적다.

2. **배경 고르기 UI 를 넣었다** (`server/public/index.html`).
   화면 위쪽에 `[🖼 게임 배경]` 버튼을 두고, 누르면 혼자 하기의 설정 모달에 있던
   배경 피커(기본 + 배경1~4, 미리보기 썸네일, 선택 표시 ✔)와 같은 모양의 모달이 열린다.
   이 버튼은 **로비에서도** 보인다. 방에 들어가기 전에도 배경을 고를 수 있어야 하기 때문이다.
   (같은 줄의 `[게임에서 나가기]` 는 방에 들어간 뒤에만 나온다.)

3. **배경을 켰을 때의 화면을 혼자 하기와 같게 맞췄다.**
   `body.has-bg` 로 body 배경에 그림 + 아주 옅은 스크림을 2단으로 깔고,
   보드·패널·힌트 패널을 반투명 유리(`backdrop-filter`)로 바꿔 배경 그림이 그대로 비쳐 보이게 했다.
   제목 글자에는 흰색 + 그림자를 줘서 밝은 배경에서도 읽히게 했다.

4. **`BackgroundManager`** — 혼자 하기와 같은 구조로 두되 저장은 `localStorage` 를 쓴다.
   사생활 보호 모드처럼 저장이 막히는 환경에서도 게임이 멈추지 않도록 읽기·쓰기를 모두 감쌌다.

**검증 중 발견해 고친 문제** — 배경을 켜고 화면을 찍어 보니 **규칙 배너 두 개가 동시에** 떠 있었다.
`.rule-banner { display: flex }` 가 브라우저 기본 `[hidden] { display: none }` 을 덮어쓰고 있었다.
`.rule-banner[hidden] { display: none }` 을 추가해 고쳤다. (033~034에서 들어간 문제였다.)

**검증**

## 036 · 2026-08-30 · 스무고개 LLM 자동 연결 + 제시어 맞추기 중복 답 안내

**요청한 내용**

> 단어 연결 게임 - 멀티플레이에서 AI 스무고개를 실행시 llm을 자동으로 연결해서 진행하고 제시어 맞추기에서 중복 답을 선택시에는 중복한 답이라고 표시하고 답을 다시 선택하도록 한다

**AI가 한 일**

### 1) AI 스무고개 — LLM 자동 연결

사람이 [연결] 같은 것을 누를 필요가 없도록, 서버가 **세 지점에서 알아서** 붙게 했다.
`OllamaHintGenerator.ensureReady()` 하나로 모으고 거기에서만 연결·모델 선택·예열을 처리한다.

1. **서버를 켤 때** (`server.js`) — 기동 로그에 연결 결과를 찍는다.
   여기서 예열해 두면 첫 문제를 기다리지 않는다(예열 없으면 실측 167초).
2. **방장이 대기실에서 스무고개를 고를 때** (`ai:status`) — 상태를 묻는 김에 연결까지 끝낸다.
   예전에는 `ping()` 만 하고 예열은 따로 던져 뒀는데, 이제 한 번에 처리한다.
3. **문제를 만들 때** (`generateHints`) — 그때까지 연결이 없으면 한 번 더 붙는다.
   부르는 쪽이 잊더라도 여기서 보장된다.

곁들여 넣은 것들:

- **모델 자동 대체.** 설정한 모델이 설치돼 있지 않으면 설치된 것 중에서 골라 쓴다
  (qwen2.5 → qwen2 → llama3.2 → gemma → mistral 순). 설정을 안 고쳐도 게임이 된다.
- **재연결.** 힌트 요청이 실패하면 `markStale()` 로 표시하고 다시 붙어 본 뒤 재시도한다.
  Ollama 가 중간에 꺼졌다 켜져도 다음 판부터 자동으로 붙는다.
- **동시 호출 정리.** 여러 곳에서 동시에 불러도 실제 연결은 한 번만 하도록 진행 중인 약속을 재사용한다.
- **알림.** 연결 결과를 `quiz:ai` 로 방 전체에 알린다. 화면에는
  "🤖 AI 연결 완료 (qwen2.5:7b)" 또는 "🤖 AI 없이 진행해요" 가 뜬다.

**AI 가 없어도 게임은 그대로 진행된다**는 원칙은 유지했다.

### 2) 제시어 맞추기 — 중복 답 안내

- `Room.solvedWords` 에 이번 게임에서 맞힌 낱말을 쌓는다(게임 시작 때 비운다).
- `RoundService.submitAnswer` 가 **정답 판정보다 먼저** 중복을 확인해
  `{ correct: false, duplicate: true }` 로 되돌려 보낸다. 점수도 오르지 않고 판도 끝나지 않으며,
  제출한 사람만 안내를 받고 다시 고르면 된다(혼자 하기와 같은 규칙).
- 화면에는 `이미 찾은 단어예요! (낱말)` 이 뜨고 블록이 흔들린 뒤 선택이 풀린다.

- `createRound()` 에 `exclude` 를 넘겨 **이미 맞힌 낱말은 다음 판의 목표에서 뺀다.**
  그러지 않으면 "보드에 심어 뒀는데 정답으로는 안 되는" 이상한 판이 생긴다.

## 045 · 2026-09-01 · 블록 조작을 드래그에서 '왼쪽 클릭 선택 + 오른쪽 클릭 완성' 으로 변경

**요청한 내용**

> 블록을 선으로 이어서 정답을 맞추는 방식대신 마우스 왼쪽으로 블록을 선택한 후에 마우스 오른쪽을 눌러서 블록선택이 끝나는방식으로 변경해줘

**AI가 한 일**

1. **드래그 조작을 걷어냈다.**
   `mousedown` → `startConnect()`, `mouseover` → `continueConnect()`,
   문서 전체의 `mouseup` 으로 판정하던 흐름을 없앴다.
   드래그 중인지 기억하던 `GameState.isDragging` 도 더 필요 없어져 지웠다.

2. **왼쪽 클릭 — `pickBlock()`**
   보드에서 `click` 을 위임받아 누른 순서대로 블록을 쌓는다.
   **이미 고른 블록을 다시 누르면 그 블록부터 뒤를 모두 되돌린다.**
   드래그 때는 지나간 블록이 그대로 들어갔지만, 클릭은 한 번에 하나씩 고르는 만큼
   잘못 눌렀을 때 되돌릴 방법이 없으면 오답을 낼 수밖에 없어서 넣었다.

3. **오른쪽 클릭 — `finishSelection()`**
   `#board-container` 의 `contextmenu` 를 가로채 브라우저 메뉴 대신 '고르기 끝'으로 쓴다.
   블록 사이 빈틈에서 눌러도 되도록 `#board` 가 아니라 보드 영역 전체에서 받되,
   **힌트 패널 위에서는 가로채지 않는다** — 힌트 글은 그대로 복사할 수 있어야 하기 때문이다.
   두 글자가 안 되면 예전 `mouseup` 과 똑같이 실수로 보고 콤보 손해 없이 선택만 푼다.

4. **판정 부분은 그대로 두고 이름만 바꿨다** — `submitSelectedWord()`
   정답/오답/콤보/모드 2 처리는 손대지 않았다. 부르는 자리만 `mouseup` 에서 오른쪽 클릭으로 옮겼다.

5. **선은 그대로 남겼다.** 요청은 *조작 방식*을 바꾸는 것이고,
   클릭으로 고를 때는 **고른 순서**를 보여줄 것이 선밖에 없어서 그대로 두는 편이 낫다.

6. **화면 안내와 잔손질.**
   두 모드의 안내 배너에 `🖱 왼쪽 클릭으로 고르고 · 오른쪽 클릭으로 완성` 칩을 넣었다.
   블록에 `user-select: none` 을 줘서 빠르게 클릭할 때 글자가 끌려 선택되지 않게 했다.

**검증**

- 인라인 스크립트 파싱 → **문법 오류 없음**. 요소 id 93개 모두 존재·중복 없음,
  `onclick` 이 부르는 전역 함수 42개 모두 정의됨.
- `pickBlock` / `finishSelection` 만 떼어내 가짜 블록으로 돌리는 **검사 14건을 새로 만들어 모두 통과**했다.
  누른 순서대로 쌓이는 것, 이미 고른 블록을 다시 누르면 그 뒤가 빠지는 것,
  1개 이하로 끝내면 판정하지 않고 선택만 풀리는 것, 2개 이상이면 만들어진 낱말로 판정하는 것,
  게임이 끝난 뒤에는 아무것도 되지 않는 것.
- `isDragging` · `startConnect` · `continueConnect` · `mouseup` · `mouseover` · `mousedown` 이
  **주석 한 줄 말고는 남아 있지 않음**을 확인했다.

**짚어 둘 점**

- **멀티플레이 화면(`server/public/index.html`)은 아직 드래그 방식이다.** 같은 게임을 두 가지
  조작으로 하게 되므로 맞춰야 할 수 있는데, 이번 요청 범위 밖이라 손대지 않았다.
- 오른쪽 클릭은 터치 화면에 없다. 다만 예전 드래그 방식도 터치 이벤트를 다루지 않아
  마우스 전용이었으므로, 이번 변경으로 나빠진 것은 없다.
- **브라우저 확인은 하지 못했다.** 이 세션에서는 브라우저 도구를 쓸 수 없어서,
  실제 클릭 감각은 직접 열어 봐 주셔야 한다.


## 046 · 2026-09-01 · 멀티플레이 화면도 같은 클릭 조작으로 통일

**요청한 내용**

  두 글자 이상이면 만들어진 낱말을 `answer:submit` 으로 보내는 것,

- `isDragging` · `startConnect` · `continueConnect` · `finishConnect` ·

## 048 · 2026-09-01 · 설계서에서 조작 말고도 현재와 어긋난 서술을 정리

> 정리해줘

(047 에서 "설계서에는 조작 말고도 오래된 서술이 남아 있다 — 함께 정리할까요?" 라고 물은 것에 대한 답이다.)

## 049 · 2026-09-05 · Vultr 배포 계획 문서 작성 (IP만 치면 게임이 뜨게)

**요청한 내용**

**AI가 한 일**

1. 먼저 **지금 상태로는 왜 안 되는지**를 코드에서 직접 확인했다.
   - `server/src/server.js` — 포트 3000, `express.static(PUBLIC_DIR)` 이 `/` 에 멀티 화면(`public/index.html`)을 물린다.

     서버에 올리면 접속자가 [접속하기] 를 눌렀을 때 자기 PC를 찌른다.
   - `tools/node` 는 Windows용 `node.exe`(v24.20.0)라 리눅스 서버에서 못 쓴다.
   - `server/Dockerfile` 의 빌드 컨텍스트가 `server/` 라서, 루트에 있는 게임 파일·그림을 이미지에 넣을 수 없다.

2. 그 확인 결과를 바탕으로 `docs/03-배포/Vultr-배포-계획.md` 를 새로 썼다. 12장 구성이다.
   목표/완료 기준 → 지금 상태의 문제 → **올리기 전에 로컬에서 고칠 코드 5가지** →

3. 설계 판단을 문서에 남겼다.
   - **라우팅**: `/` 는 혼자 하기, `/multi` 는 멀티. IP만 치고 들어온 사람이 바로 놀 수 있어야 하므로
     시작 화면이 있는 혼자 하기 쪽을 `/` 로 뒀다. `express.static` 보다 라우트를 먼저 등록해야 하고
     `{ index: false }` 가 필요하다는 점까지 적었다.
   - **80 포트**: 도커 포트 매핑(`"80:3000"`)을 권장으로 골랐다. 리버스 프록시는 부품이 늘고
     WebSocket 헤더를 빠뜨리면 멀티가 통째로 죽어서, 도메인을 붙일 때 옮기는 것으로 미뤘다.
   - **파일 중복 회피**: 게임 파일을 `server/public/` 으로 복사해 두 벌로 관리하면 한쪽만 고치게 되므로,

   - **Ollama**: 7B 모델은 RAM 8~16GB를 요구해 게임 서버 사양의 10배가 든다. 1단계에서는 서버에 올리지 않고,
     멀티 스무고개는 서버의 확정 힌트(글자 수·초성)로 진행되며 혼자 하기는 접속자 본인 PC의 Ollama를
     쓴다는 점(그래서 그 PC에 `OLLAMA_ORIGINS` 가 필요하다는 점)을 정리했다.

4. `CLAUDE.md` 의 "이 폴더 안의 것만으로 돌아가야 한다" 원칙과 충돌하는 부분을 문서에 명시했다.

## 050 · 2026-09-05 · 배포 1단계 — 주소를 둘로 나누고 도커를 80 포트로

**요청한 내용**

> 1단계 코드 수정을 지금 진행하고 진행한 내용은 별도의 문서로 남겨줘

**AI가 한 일**

1. **`server/src/server.js` — 화면을 두 주소로 나눴다.**
   `/` 는 혼자 하기 시작 화면, `/multi` 는 멀티플레이다. 주소만 알고 들어온 사람은 방 코드를
   받을 데가 없어서 멀티 대기실이 첫 화면이면 아무것도 못 하기 때문이다.
   이 라우트는 `express.static` **보다 먼저** 등록해야 하고(static 이 `/` 에 `index.html` 을 먼저 준다),
   같은 이유로 static 에 `{ index: false }` 를 줬다.

2. **같은 파일 — 로컬 실행에서도 `/` 가 되게 했다.**
   혼자 하기 파일과 그림은 저장소 루트에 있고 `server/public/` 에는 없다. 도커는 빌드할 때 넣어 주지만
   `서버 켜기.bat` 로 켜면 루트에 그대로 있으므로, 두 경우를 모두 받도록 `LOCAL_RUN` 판정을 넣었다.
   루트를 통째로 열지 않으려고 배경은 이름 4개를 목록으로 못박고 아이콘은 `/assets` 에만 붙였다.
   컨테이너에서는 `ROOT_DIR` 이 `/` 지만 게임 파일이 없어 `LOCAL_RUN` 이 false 가 된다.

3. **`word_connection_game.html` — 멀티 주소를 자동으로 뽑게 했다 (3곳).**
   - `DEFAULT_MULTIPLAYER_URL` 을 `location.origin + '/multi'` 로. 예전 `localhost:3000` 고정값은
     인터넷에 올리면 접속자가 **자기 PC**를 찌르게 만든다. `file://` 로 연 경우에만 옛 값을 쓴다.
   - `getMultiplayerUrl()` — 저장값이 기본값을 이기므로, 예전에 [접속하기] 를 눌러 본 사람은
     `http://localhost:3000`(= 이제 시작 화면)으로 되돌아와 영영 멀티로 못 간다.
     저장값이 지금 보고 있는 서버를 가리키면 새 주소로 바꾸고, 다른 PC 주소는 건드리지 않는다.
   - `probeMultiplayerServer()` — `target + '/healthz'` 가 `/multi/healthz` 가 되므로
     `new URL('/healthz', target)` 로 서버 뿌리를 보게 고쳤다.
   - `chooseMultiplayer()` — 서버를 통해 열렸으면 서버는 이미 켜져 있으므로
     '서버 켜기.bat 을 더블클릭' 안내를 숨긴다.

4. **`server/Dockerfile` · `server/docker-compose.yml` — 루트 원본을 이미지에 담고 포트를 80으로.**
   빌드 컨텍스트를 저장소 루트(`context: ..`)로 올려, 파일을 복사해 두 벌로 관리하는 일을 피했다.
   배경 그림은 파일명이 한글이라 Dockerfile 에 직접 적으면 인코딩 문제로 못 찾을 수 있어
   `COPY *.png` 로 받고, 나머지 루트 png 는 `.dockerignore` 에서 뺐다.
   바깥 포트를 `80:3000` 으로 두어 주소창에 IP만 쳐도 들어오게 했다.

5. **루트 `.dockerignore` 를 새로 만들었다.** 도커는 컨텍스트 최상단의 것만 읽으므로
   `server/.dockerignore` 는 이제 적용되지 않는다(그 파일 맨 위에 안내를 적었다).
   이게 없으면 `tools/node` 106MB 와 `.git` 52MB 가 빌드에 통째로 실려 간다.

6. **안내 문구 정리** — `server/public/index.html` 의 재시도 링크·오류 문구를 `/multi` 기준으로,

7. 진행 내용을 **`docs/03-배포/1단계-코드수정-기록.md`** 에 따로 남기고,
   `Vultr-배포-계획.md` 맨 위에 1단계 완료 표시와 그 문서 링크를 붙였다.

## 053 · 2026-09-05 · 저장소 루트에 진입점 package.json 을 둔다

**요청한 내용**

> 루트에 package.json하나 둔다

**AI가 한 일**

1. 저장소 루트에 `package.json` 을 만들었다. 실제 서버 코드는 그대로 `server/` 에 있고,
   루트의 것은 **진입점 역할만** 한다.

   ```json
   "scripts": {
     "start": "node server/src/server.js",
     "postinstall": "npm install --omit=dev --prefix server"
   }
   ```

   - `start` — Render 가 `npm start` 를 부르면 `server/` 의 서버가 켜진다.
   - `postinstall` — `npm install` 뒤에 npm 이 자동으로 이어 실행해 `server/` 의 의존성을 설치한다.
     **의존성 목록을 두 군데에 적지 않으려고** 이렇게 했다. 라이브러리를 추가할 때는
     지금까지처럼 `server/package.json` 만 고치면 된다.
     (`server/package.json` 에는 `postinstall` 이 없으므로 무한히 되돌지 않는다.)

2. 이 파일 하나로 052 에서 적어 둔 Render 설정 두 가지가 함께 없어졌다.
   - Root Directory 를 `server` 로 지정할 필요가 없다 → **비워 두면 된다.**
   - 루트에는 `Dockerfile` 이 없으므로 런타임이 Docker 로 잘못 잡힐 일이 없다.
     (`server/Dockerfile` 은 빌드 컨텍스트가 저장소 루트라는 전제로 쓰여 있어 Render 가 그것으로
     빌드하면 실패한다. Vultr 용이다.)

3. `docs/03-배포/Render-배포-절차.md` 를 그에 맞게 고쳤다 — 설정 표에서 Root Directory 를
   "비워 둡니다"로, 3.1 항목을 "루트를 보므로 Node 로 잡힌다"로 바꾸고,
   루트 `package.json` 이 무엇을 하는 파일인지 설명을 넣었다.
   `server/README.md` 에도 루트에서 켜는 방법과 "의존성은 server/package.json 에만 적는다"를 적었다.

**검증**

- 루트에서 `npm install --no-audit --no-fund` 를 실제로 돌렸다. `postinstall` 이 이어 실행되어

## 060 · 2026-09-05 · 모드 3 최종 결과에 '몇 개 맞혔는지'를 제대로 공개한다

**요청한 내용**

> 모드 3 산업재산권 문제를 얼마나 맞췄는지 끝난 후에 공개되도록 한다

**먼저 밝혀 둘 것**

055 에서 만든 최종 결과창에 `N문제 중 M문제를 맞혔어요` 한 줄과 문제별 ⭕/❌ 목록이
이미 들어 있었다. 다만 **가장 궁금한 숫자가 눈에 띄지 않았고, 목록이 스타일 없이 나오고 있었다.**
그래서 이번에는 그 화면을 제대로 고쳤다.

**AI가 한 일**

1. **큰 숫자를 점수에서 '맞힌 개수'로 바꿨다.** 이 화면에서 가장 궁금한 것은 몇 개를 맞혔나지
   점수가 아니다. 이제 `4 / 7` 이 크게 뜨고, 점수는 그 아래 줄(`⭐ 점수 23점`)로 내렸다.
   부제에는 `7문제 중 4문제를 맞혔어요 · 정답률 57%` 로 정답률까지 적는다.

2. **문제별 목록에 문제 문장을 함께 적는다.** 예전에는 정답만 나와서, 무엇을 틀렸는지 알려면
   정답을 보고 문제를 되짚어야 했다. 이제 한 줄에 `⭕/❌ + 문제 문장(42자까지)` 이 나오고,
   그 아래 작은 글씨로 `정답: …` 이 붙는다. 정답이 여러 개인 문제를 맞힌 경우에는
   `내가 만든 답: …` 도 함께 적어, 어느 것으로 맞혔는지 알 수 있게 했다.

3. **목록이 스타일 없이 나오던 문제를 고쳤다.** 055 에서 이 목록을 만들 때 CSS 에 없는 클래스

   모드 2가 쓰는 `qr-no` · `qr-body` · `qr-cat` · `qr-score` 와 틀린 줄을 흐리게 하는 `.missed` 였다.
   그 클래스로 바꿔 모드 2 결과창과 같은 모양이 되게 했다.

4. **진행 중에는 여전히 알려 주지 않는다.** 요청이 "끝난 후에 공개"이므로, 문제마다 뜨는
   결과창은 그대로 두었다(그 창은 이번 문제의 정답과 누적 점수만 보여 준다).
   지금까지 몇 개를 맞혔는지는 마지막 결과창에서 처음 나온다.

**검증**

- 구문 오류 0개. 참조 id **133개 전부 존재**(새로 넣은 `examFinalPoints` 포함).
- **JS 가 붙이는 클래스가 CSS 에 있는지 기계로 확인하는 검사를 새로 돌렸다.**
  `makeEl` 로 붙이는 **28개 클래스 전부 CSS 에 정의돼 있다.** 3번 문제가 바로 이 검사로
  드러났을 종류라, 앞으로도 같은 실수를 잡을 수 있게 검사 방법을 기록에 남긴다.
- 3019 포트로 띄워 페이지 200 과 결과창 마크업(`examFinalScore` 가 `0 / 0`,
  새 줄 `examFinalPoints`)이 나오는 것을 확인했다.

**짚어 둘 점**

- 브라우저에서 한 판을 끝까지 풀어 본 것은 아니다. 마크업·클래스·구문까지 기계로 확인했다.
